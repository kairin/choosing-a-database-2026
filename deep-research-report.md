# Adversarial Review: Choosing a Database in 2026

## Executive assessment

The write-up has a **good high-level decision philosophy but several claims that are too absolute, benchmark-like without evidence, or already stale as of 17 September 2026**. Its central idea — choose according to data model, workload and operational constraints rather than searching for a universally “best” database — is sound. The broad positioning of PostgreSQL for general-purpose transactional applications, SQLite for embedded/local storage, DuckDB for embedded analytics, MongoDB for document-oriented workloads and Doltgres for version-controlled relational data is also broadly defensible. Official documentation for these products supports those distinctions. citeturn20view0turn29search3turn22view5turn25view0

The strongest problems are more specific:

The biggest danger is that several implementation details are presented as invariant truths when they are really **version-dependent features, benchmark observations, or workload-dependent performance outcomes**.

## Where the five core database descriptions survive scrutiny

**PostgreSQL remains the strongest candidate for the “general-purpose default” label**, provided “default” means a conventional centralised application database rather than every possible database workload. PostgreSQL 18 is the current stable major line as of September 2026, with 18.6 among the August 2026 maintenance releases. PostgreSQL provides MVCC, declarative partitioning and sophisticated relational functionality while also supporting semi-structured data through `jsonb`. The PostgreSQL documentation states that `jsonb` stores data in a decomposed binary format and supports indexing, including GIN indexing, so the original argument that PostgreSQL can cover substantial document-like workloads is well founded. citeturn0search0turn19view0turn19view1turn19view2

The original goes too far, however, when it implicitly treats PostgreSQL JSONB as a wholesale substitute for MongoDB. PostgreSQL's own documentation recommends that JSON documents have a “somewhat fixed structure” and points out that an update acquires a row-level lock on the entire row, making very large JSON documents potentially contentious under concurrent updates. The better conclusion is that JSONB can eliminate the need for a separate document database **when the semi-structured portion naturally belongs inside an otherwise relational transactional model**; it does not invalidate the document-database model. citeturn19view0

The PostgreSQL graph statement needs the strongest correction. SQL/PGQ/property-graph functionality is documented for **PostgreSQL 19 development**, not PostgreSQL 18 stable. PostgreSQL 19 was still in beta in August 2026, and on 2 September 2026 PostgreSQL's Release Management Team publicly raised unresolved design and dump/restore concerns and stated that it believed reverting the feature from PostgreSQL 19 would be preferable. Therefore, as of 17 September 2026, an architecture decision should **not treat SQL/PGQ as a released PostgreSQL production capability**. citeturn11search0turn16search0turn14search0

**SQLite is substantially more production-capable than many developers assume, but the original uses the wrong evidence to make that point.** SQLite's own guidance explicitly supports embedded devices, edge applications, application file formats, local caches and even low-to-medium-traffic websites. It describes fewer than 100,000 hits per day as a conservative web guideline and notes demonstrations at ten times that traffic, while simultaneously warning that write-intensive, multi-server and high-concurrency systems are better candidates for a client/server database. That is a much more defensible statement than “10 million users”. citeturn20view0

WAL mode improves SQLite's concurrency because readers can proceed while a writer is active, and SQLite says WAL is significantly faster in many scenarios. But **WAL does not create multi-writer concurrency**: SQLite explicitly says there can still be only one writer at a time. Moreover, `PRAGMA synchronous` changes the durability/performance balance; under `NORMAL`, for example, transactions can be lost following a power failure or hard reset. Consequently, a standalone “10,000 writes/sec” figure without hardware, transaction size, batching, journal/checkpoint configuration and durability requirements is not a useful database-selection fact. citeturn20view1

The backup claim deserves an outright correction. SQLite warns that taking a file copy while a transaction is active can create a copy containing a mixture of old and new pages and therefore a corrupt backup. Safe approaches include the SQLite backup API, `VACUUM INTO` and `sqlite3_rsync`; a filesystem copy is safe when no transaction is in progress, with the additional requirement to preserve relevant journal/WAL files where applicable. The “single file means `cp db.sqlite` is a backup strategy” formulation should therefore be deleted. citeturn28view15turn28view16turn28view17

**DuckDB's positioning is among the most accurate parts of the original, although the concurrency row is becoming outdated.** DuckDB describes itself as an analytical database and supports direct querying of Parquet and other formats; its Parquet reader performs automatic projection and filter pushdown and can use Parquet zonemaps to avoid reading irrelevant data. Current DuckDB documentation also lists first-class integrations/extensions for Delta, Iceberg, HTTP/S3, Azure and other data sources. citeturn28view11turn23view0turn29search3

The claim about analytical SQL is also broadly supported. DuckDB provides native `ASOF JOIN` for temporal/ordered data and positional joins in addition to conventional joins. That is a real SQL-language advantage for certain analytical workloads, not merely benchmark marketing. citeturn28view10

Where the matrix needs updating is concurrency. DuckDB's current documentation says multiple threads in a single process can perform writes using MVCC and optimistic concurrency control when their updates do not conflict. It also documents the Quack remote protocol for multi-process access, although that functionality was still described as beta in the DuckDB 1.5 timeframe. Thus “bulk changes, not high-frequency OLTP” remains a useful architectural warning, but “DuckDB basically has no concurrent writing” would now be wrong. citeturn5view0

DuckDB really does enforce foreign keys, but even that deserves a footnote: its documentation warns that constraints impose write/load cost and that automatically created ART indexes have some current limitations. A tick mark in a comparison table is technically correct but hides operational differences from PostgreSQL's mature OLTP constraint implementation. citeturn23view0

**MongoDB's document-model description is reasonable; its optimiser description is not.** MongoDB's own modelling guidance recommends embedding when related information is normally queried or updated together, but recommends references for cases such as high-cardinality children, unbounded growth, excessive duplication or entities written independently in write-heavy workloads. This is much more nuanced than “MongoDB eliminates joins”: good MongoDB design deliberately chooses between embedding and referencing according to access patterns. citeturn22view5

Likewise, “flexible schema” does not mean “no enforceable schema”. MongoDB allows validation rules for types, value ranges and document structures, and by default rejects inserts or updates that violate configured validation rules. A fair description is therefore **schema-flexible with optional database-enforced document validation**, not “schemaless”. citeturn22view4

The foreign-key criticism is directionally fair. MongoDB's modelling documentation describes references between collections and points to application logic, transactions and triggers for maintaining consistency across duplicated or related data; it does not provide PostgreSQL-style declarative foreign-key constraints between collections. MongoDB does, however, provide multi-document distributed transactions, so “all integrity is simply the application's problem” would also be too crude. citeturn22view5

The aggregation-pipeline criticism is the most clearly incorrect MongoDB statement in the original. MongoDB has an explicit aggregation optimisation phase. Its optimiser can move `$match` filters ahead of projection stages, move filters ahead of `$sort`, coalesce stages, and combine eligible `$lookup`, `$unwind` and `$match` operations. MongoDB is **not equivalent to a relational cost-based optimiser that is free to reorder an arbitrary graph of SQL joins**, but neither does it simply execute every pipeline stage exactly where the developer typed it. citeturn7view0

Finally, “large binary objects” is a weak reason to select MongoDB. A normal BSON document is limited to 16 MiB; GridFS exists specifically to store files larger than that by splitting them into chunks. GridFS can certainly be appropriate for some applications, but that is different from saying MongoDB has a structural advantage for large object storage. citeturn6search19

**Doltgres is genuinely interesting and the version-control description is real, but it receives the most favourable spin in the original matrix.** DoltHub released Doltgres 1.0 on **6 August 2026**, with Git-style data/schema versioning and PostgreSQL-oriented protocol/tool compatibility. The “Git for relational data” description is therefore fair. citeturn25view0

The phrase “99% Postgres-compatible” requires prominent qualification. DoltHub says the 99% figure comes from passing more than 99% of a 5.6-million-query SQL logic test checked against PostgreSQL plus integration testing of supported clients. That is useful evidence, but it is not mathematically equivalent to “99% of all PostgreSQL functionality”. The same Doltgres 1.0 announcement lists PostGIS, vector indexes, row-level security, collation support and better DDL support on its post-1.0 roadmap, demonstrating why a single percentage cannot stand in for feature compatibility. citeturn25view0

Calling Doltgres “Postgres-level” for OLTP is particularly misleading. DoltHub's own launch post reported Doltgres at approximately **2.7 times slower than PostgreSQL** on the cited sysbench comparison. That does not mean Doltgres is unusably slow — latency requirements are application-specific — but it means PostgreSQL-equivalent query performance should not be assumed. citeturn25view0

The original explanation that the slowdown exists “because reads traverse a content-addressed tree” is also too confident about causality. Doltgres does use Dolt's underlying versioned storage/query technology, but the defensible evidence is the measured vendor benchmark, not a monocausal explanation for every performance difference. The decision should therefore be: **pay a measurable compatibility/performance/maturity premium only when first-class branching, diffing, merging and data history create enough value to justify it.** citeturn25view0

## The “other notable options” section also needs qualification

**MariaDB:** describing MariaDB as having a pluggable storage-engine architecture is correct; MariaDB's documentation explicitly describes that architecture and engines such as InnoDB, MyISAM and Aria, while MariaDB separately maintains its ColumnStore analytical offering. What should be removed is the implication that simply mixing engines automatically gives one seamless “OLTP + OLAP in one schema” architecture. Storage-engine-specific capabilities, replication behaviour, indexing and operational characteristics still need to be evaluated independently. citeturn28view6turn27view7

**ClickHouse:** the “large-scale OLAP” positioning is sound, and the statement that it lacks relational foreign keys is supported by ClickHouse's own documentation, which explicitly says it does not implement foreign-key constraints. The JSON description needs updating, however. Modern ClickHouse JSON storage uses typed/dynamic paths and subcolumns, but a `max_dynamic_paths` limit controls how many are independently materialised; excess paths can be stored in a shared data representation. Saying simply “every path becomes a typed subcolumn” hides an important storage/performance mechanism. citeturn24search19turn28view13turn28view14

**Redis:** “not a primary database” should become **“often used as a cache or specialised low-latency data store, but persistence requirements determine whether it can safely be authoritative.”** Redis offers RDB snapshots, AOF logging, a combination of both, or no persistence. With the default AOF `everysec` policy, Redis documents a possible loss window of roughly one second after a disaster; it also recommends combining persistence mechanisms where stronger data safety is required. That makes Redis qualitatively different from saying “it is only a cache”. citeturn25view3

**CockroachDB:** “distributed SQL with PostgreSQL compatibility and strong consistency” is broadly fair but should not read as “distributed PostgreSQL”. CockroachDB speaks the PostgreSQL wire protocol and supports most PostgreSQL syntax/types/drivers rather than every PostgreSQL capability. More importantly, CockroachDB defaults to `SERIALIZABLE` isolation, and its own examples show concurrency conflicts producing transaction-retry errors that applications may need to handle. Stronger distributed transactional semantics therefore come with behavioural and latency consequences that should be part of the architecture decision. citeturn29search0turn29search4turn27view1

**TiDB:** similarly, “MySQL-compatible” should mean compatibility surface rather than drop-in identity. PingCAP maintains an explicit MySQL compatibility document because there are behaviours and features requiring migration review. Grouping TiDB and CockroachDB together is useful at the architectural level — distributed SQL — but they should not be treated as interchangeable implementations merely because one presents a MySQL-oriented surface and the other a PostgreSQL-oriented one. citeturn27view3

The original category **“Snowflake / Databricks: cloud data warehouses”** is also too coarse for a serious selection document. More importantly, neither belongs in a direct five-way comparison with SQLite, PostgreSQL or MongoDB unless the requirement itself is an analytical data platform rather than the primary transactional store. The first branching question should be **OLTP system of record versus analytical platform**, not “which database brand is better”.

The vector-database recommendation similarly needs to resist category inflation. “We use embeddings” is no longer sufficient justification for operating a separate vector database. The right question is whether vector retrieval is a dominant workload requiring capabilities or scale that the system-of-record database cannot meet. Otherwise, introducing a second authoritative storage system creates replication, freshness, failure-recovery and consistency obligations that need to be justified by measured retrieval requirements.

## The operational issues the original underweights

The largest weakness of the original framework is not any individual feature error; it is that it still treats **feature matrices as more important than operational topology**. SQLite's own selection guide makes topology one of its first questions: if the data is separated from the SQL-issuing application by a network, or many independent writers need concurrent access, SQLite recommends considering a client/server system. Conversely, if the data is local to one device/application and writer concurrency is modest, the absence of a server can be a major architectural advantage. citeturn20view0

Likewise, “scale” should be decomposed rather than treated as one scalar. There is a profound difference between a 5 TB database with one writer, a 100 GB database receiving tens of thousands of independent transactions, a multi-region application requiring synchronous transactional guarantees, and a 20 TB Parquet dataset queried periodically by analysts. The database names in the original list are optimised for different members of that set; raw data volume alone does not identify the right architecture. SQLite, for example, explicitly distinguishes its single-writer constraint from raw file-size limits, while DuckDB optimises analytical scanning and pushdown into files rather than behaving like a high-concurrency transaction server. citeturn20view0turn28view11turn5view0

Durability also needs to be an explicit axis. A claim such as “X writes per second” is almost meaningless without stating whether each transaction requires durable media synchronisation. SQLite explicitly documents different behaviour depending on `synchronous` settings, including performance/durability trade-offs, while Redis exposes similarly explicit AOF `fsync` policies ranging from every operation to every second to relying on the operating system. Throughput numbers that omit those settings are therefore poor architecture evidence. citeturn20view1turn25view3

Consistency semantics deserve the same treatment. PostgreSQL uses MVCC but defaults to `READ COMMITTED`; CockroachDB defaults to `SERIALIZABLE`; MongoDB provides single-document atomicity and also supports distributed transactions; SQLite serialises writers. A generic matrix cell reading “strong consistency” misses how application-visible behaviour differs, including retries, contention and transaction scope. citeturn19view2turn27view1turn22view5turn20view1

Operational maturity should also be treated separately from SQL compatibility. Doltgres 1.0 made explicit commitments around forward storage compatibility and a stable version-control interface, which is important progress, but its 1.0 announcement simultaneously identified substantial PostgreSQL functionality for future implementation. That makes it reasonable for a version-control-centric application and much harder to justify as a transparent PostgreSQL substitute for an application that depends heavily on the wider PostgreSQL surface. citeturn25view0

Finally, benchmarking needs a stricter standard throughout the document. Statements such as “10× faster”, “10,000 writes/sec”, “millions of users” or even “2.7× slower” have value only when the workload, data distribution, hardware, durability setting, concurrency and software versions are known. The difference is that DoltHub at least identifies its 2.7× number as a sysbench comparison, whereas the SQLite numbers in the proposed text are presented as universal capabilities. SQLite's own documentation instead emphasises workload characteristics and explicitly warns that the appropriate answer changes with writer concurrency. citeturn25view0turn20view0turn20view1

## A stronger database-selection framework for 2026

A more defensible selection process starts by eliminating whole database categories before comparing products.

| Requirement | First candidate to investigate | Reason / principal caveat |
|---|---|---|
| Conventional SaaS/API with relationships, transactions, joins and multiple concurrent writers | **PostgreSQL** | Strong general-purpose relational baseline with JSONB where moderate schema flexibility is needed. Do not assume unreleased PostgreSQL 19 features are available in PostgreSQL 18. citeturn19view0turn19view2turn14search0 |
| Mobile, desktop, appliance, edge node or application-local durable state | **SQLite** | Eliminates the database server and works naturally with device-local storage; avoid it when many writers must mutate the same database concurrently. citeturn20view0 |
| Server application where each tenant/user can naturally have an independent local DB file | **SQLite is genuinely viable** | Per-database writer serialisation can cease to be the bottleneck when workloads are isolated into independent files; SQLite itself describes this application-server pattern. citeturn20view0 |
| Notebook, data-science workload, embedded ETL or local exploration of Parquet/object storage | **DuckDB** | Native analytical orientation, direct file querying, projection/filter pushdown and analytical join primitives. citeturn29search3turn28view10turn28view11 |
| Production analytics over large columnar datasets with dedicated serving infrastructure | **ClickHouse or a warehouse/lakehouse platform** | ClickHouse is architecturally analytical rather than a relational OLTP system and does not enforce foreign keys. citeturn24search19 |
| Domain objects map naturally to self-contained aggregates and schema variations are intrinsic | **MongoDB merits evaluation** | Embedding can simplify access when related data is consumed together, while references are recommended for high-cardinality, independently evolving relationships. citeturn22view5 |
| “We want MongoDB merely because requirements may change” | **Start by testing PostgreSQL JSONB instead** | PostgreSQL supports indexable semi-structured JSON while retaining relational constraints; MongoDB itself recommends deliberate schema planning despite having a flexible model. citeturn19view0turn22view4turn22view5 |
| Data/schema branches, merges, diffs and reproducible versions are a first-class product requirement | **Doltgres** | This is precisely the capability around which Doltgres is differentiated, but PostgreSQL compatibility and performance still require workload-specific qualification. citeturn25view0 |
| Horizontal transactional scale / multi-region failure tolerance is a primary requirement | **Evaluate distributed SQL such as CockroachDB or TiDB** | This is a fundamentally different operational trade-off from running ordinary PostgreSQL/MySQL; compatibility does not imply identical behaviour, and distributed transactions introduce different latency/retry considerations. citeturn27view1turn27view3turn29search4 |
| Sub-millisecond-ish access to specialised data structures, ephemeral state, queues/counters or caching | **Redis may fit** | Redis can be ephemeral or persistent; whether it is authoritative should follow from the required durability model rather than a blanket “cache only” rule. citeturn25view3 |

There is also a useful **negative decision rule**: do not introduce a specialist database merely because it supports one attractive data type. PostgreSQL having JSONB does not automatically make it the best document store; MongoDB having `$graphLookup` does not make it a graph database; ClickHouse accepting JSON does not make it an OLTP document database; Redis offering persistence does not make it the natural system of record; DuckDB enforcing foreign keys does not make it a high-concurrency transactional server. The dominant access pattern and operational topology should decide the category first, with individual features breaking ties afterwards. citeturn19view0turn7view0turn28view14turn25view3turn23view0turn5view0

## Recommended replacement for the original conclusion

The strongest defensible conclusion is more conditional than “always start with PostgreSQL”:

> **For a conventional networked application with multiple concurrent writers, relational business data and no unusual distribution requirement, PostgreSQL remains an excellent baseline against which alternatives should justify themselves.** PostgreSQL combines mature MVCC-based transactional behaviour with relational constraints and indexable JSONB, but prospective PostgreSQL 19 features such as SQL/PGQ should not be counted as stable PostgreSQL 18 capabilities. citeturn19view0turn19view2turn0search0turn14search0
>
> **Choose SQLite when the database naturally belongs with the application rather than behind a database server.** It is a serious production engine for local, embedded, edge and some server-side patterns, but it remains a one-writer-at-a-time database and should not be justified through universal claims about millions of users or fixed writes-per-second figures. Use SQLite's supported backup mechanisms rather than blindly copying a live database file. citeturn20view0turn20view1turn28view15
>
> **Choose DuckDB when analytics is the workload rather than merely a feature.** Its ability to query Parquet and lakehouse/object-storage data directly, push filters and projections into those scans, and express specialised joins makes it unusually effective as an embedded analytical engine. Its write concurrency is more capable than older summaries suggest, but that still does not turn it into the natural replacement for PostgreSQL in high-frequency multi-client OLTP. citeturn28view10turn28view11turn5view0
>
> **Choose MongoDB when document aggregates are genuinely the natural unit of storage and access.** Do not select it merely for “schema flexibility”: MongoDB encourages intentional schema design and provides validation, while PostgreSQL can already accommodate substantial semi-structured data. MongoDB's lack of SQL-style cross-collection foreign keys is a real architectural trade-off, but its aggregation engine is considerably more optimised than a literal stage-by-stage execution description suggests. citeturn22view4turn22view5turn7view0
>
> **Choose Doltgres when version control of live relational data is valuable enough to become an architectural requirement rather than a nice-to-have.** Doltgres 1.0, released on 6 August 2026, makes branching/versioning its defining capability; however, the “99% PostgreSQL-compatible” figure is a test-suite result rather than a promise of complete PostgreSQL feature equivalence, and DoltHub's own launch material measured it at roughly 2.7× PostgreSQL's time on the cited sysbench comparison while listing additional PostgreSQL features on its roadmap. citeturn25view0
>
> **Escalate to a distributed or specialised database only when the workload proves that a simpler architecture is inadequate.** CockroachDB-style distributed SQL, ClickHouse-style analytical storage and persistent Redis each solve legitimate problems, but they introduce different consistency, failure, operational and modelling assumptions. Those costs should buy a requirement you actually have, not merely a feature that looks attractive on a comparison matrix. citeturn27view1turn24search19turn25view3

The resulting hierarchy is therefore not **PostgreSQL > SQLite > DuckDB > MongoDB > Doltgres**. It is closer to:

**centralised transactional application → PostgreSQL; local/application-owned transactional data → SQLite; embedded analytical computation → DuckDB; document-aggregate-centric application → MongoDB; version-controlled relational data → Doltgres; large-scale analytical serving → ClickHouse/warehouse-class systems; mandatory distributed transactional topology → distributed SQL.**

That is the durable part of the original thesis. The database should follow the **transaction model, access pattern, concurrency topology, durability target, distribution requirement and operating model**. Feature checklists — and especially decontextualised throughput numbers — should come afterwards. citeturn20view0turn20view1turn22view5turn28view11turn27view1turn25view0
